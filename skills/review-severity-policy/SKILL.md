# 严重度判定策略（v1.0 两轴锚定）

> 本 skill 是 ai-review-method 的**可插拔策略插件**。替换本 skill = 更换定级策略，主流程不动。
> 设计原则：**LLM 不直接给数字，只判事实，代码映射数字**——保证同一条 issue 无论跑几次级别不变。

## 一、两轴事实判断（LLM 输出，非数字）

每条 issue 必须给出两个**事实判断**字段（不要输出严重级别数字）：

**轴 1 `trigger`（必然性）**：
- `real`：存在真实触发路径（确定性逻辑错误，必然/可直接利用）
- `hypothetical`："若 X 失败则…"类故障分支（需特定故障才发生，无真实必然触发路径）
- `style`：纯风格，不涉及行为正确性

**轴 2 `impact`（后果）**：
- `fatal`：数据丢失 / 崩溃 / 资金损失 / 严重越权
- `functional`：功能错误 / 数据不一致 / 安全风险
- `minor`：可恢复的降级 / 防御性缺失
- `none`：可读性 / 命名 / 风格

## 二、映射表（确定性，代码/规则实现）

| 级别 | 语义 | 判定锚点 |
|------|------|---------|
| 1 | 建议 | 纯风格/命名/可读性 |
| 2 | 轻微 | 假设性 + 轻微后果（防御性建议） |
| **3** | **必修（基线）** | 有路径 + 轻微 / 明确约定违反 / 假设性 + 安全后果 |
| 4 | 严重 | 有路径 + 功能错/数据不一致/安全风险 |
| 5 | 致命 | 有路径 + 数据丢失/崩溃/越权 |

### 2.1 两轴组合矩阵（本表的完整逻辑）

> 上面的表是"结果表"（同级别的锚点合集），真正的逻辑是 **trigger × impact 组合出数字**：

```
                    影响程度 impact →
                    无 none     轻微 minor    功能错/安全 functional   致命 fatal
必然性  ┌──────────────────────────────────────────────────────────────────┐
trigger │                                                                  │
↓       │                                                                  │
 style  │     1 建议      │     1 建议     │       1 建议      │    1 建议  │
 (纯风格)│  (不涉及行为)   │               │                  │            │
        ├─────────────────┼───────────────┼──────────────────┼────────────┤
 hypo   │     2 轻微      │     2 轻微    │     3 必修(不阻塞)│  3 必修    │
 (假设性)│ (防御性建议)    │  (防御性建议)  │  ← 关键规则：      │ (不阻塞)   │
 "若X失败"│               │               │   假设性最高 3    │            │
        ├─────────────────┼───────────────┼──────────────────┼────────────┤
 real   │     3 必修      │     3 必修    │     4 严重        │  5 致命    │
 (真实路径)│ (约定违反/轻微) │  (约定违反)    │  (拦合并)         │  (拦合并)   │
        └─────────────────┴───────────────┴──────────────────┴────────────┘
```

**核心设计意图（一句话）**：最贵的误报 = "假设性问题却标成 4/5 级"（会误拦合并）。所以：
- `hypothetical`（"若 X 失败则…"）**封顶 3**——无论话术多吓人，无真实必然触发路径就只能是"必修但不阻塞"
- 只有 `real`（有真实路径）才能进 4/5 → 拦合并
- LLM 只判"真会发生吗 + 多严重"，数字由矩阵机械决定，无法"感觉"出数字

**硬性约束（v1.0 不可改）**：
- 5 必须同时满足"有路径 + 致命后果"，缺一降 4
- 映射是确定性的：`(trigger, impact) → 数字`，不靠模型感觉

**软性参数（v1.0 默认值，可校准）**：
- 假设性故障最高 3（不升 4/5）——**这是"非硬性"部分，PR 样本积累后可调**
- 约定违反 = 3
- 必修线 baseline = 3；阻塞线 block = 4（≥4 拦合并）

## 三、判定流程

```
LLM 审查时对每条 issue 输出:
  "trigger": "real" | "hypothetical" | "style"      ← 事实判断
  "impact": "fatal" | "functional" | "minor" | "none" ← 事实判断
      ↓
代码映射: 两轴 → 1-5(确定性表, 见上)
      ↓
门禁: ≥3 评论标"必修"(不拦合并) / ≥4 拦合并
```

## 四、可插拔接口（如何替换本策略）

1. 新建 `review-severity-policy-<variant>` skill（如 `-calibrated-v2`），内容 = 本结构 + 校准后的软性参数
2. 在 ai-review-method 的配置里指向新 skill 名
3. 主流程零改动

**校准方法论（PR 样本积累后）**：
1. 收集历史 issues，人工标二分类"必须修/可不修"（二分类最容易标，不纠结数字）
2. 看两类样本在映射后的分布，找区分度最大的切分点
3. 基线不是先定的，是数据告诉你的

## 五、当前版本限制（诚实声明）

- 本策略基于**有限 PR 样本**（devops-dashboard 数轮评审）归纳，未经大规模数据校验
- 软性参数（假设性最高 3、约定违反=3）是"合理默认"，非经验证事实
- 建议：跑 20-50 个 PR 后，按"校准方法论"重做一版（v1.1 或独立 variant）
