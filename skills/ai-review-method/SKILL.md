# AI 代码评审方法论壳（v1.0）

> 本 skill 是从 `Tania-X/ai-tools` 的 pr-review 引擎中**提取的方法论**（2026-08-20），
> 作为"规格书"独立演进；ai-tools 代码实现向本规格对齐。
> **执行评审前，先加载插件 skill `review-severity-policy` 获取当前严重度策略。**

## 一、触发条件

- 需要评审一个 PR/MR 的 diff（打开、更新、或人工要求）
- 评审对象：新增/修改的代码行（diff 中 `+` 行），只评本 PR 引入的问题
- 平台无关：diff 来自 GitHub/GitLab 均可，本方法只消费"diff + 仓库"两个输入

## 二、上下文收集（评审前必做）

### 2.1 约定文件注入（静态上下文）
自动收集仓库约定/契约文件，注入 prompt（按配置顺序，超预算即停）：
- 默认：`AGENTS.md` / `README` / `docs/**` / `spec/**`（前 150 行/文件，总预算 ~8KB）
- 目的：让评审结合契约与设计意图下结论，**显著降低设计意图类误报**

### 2.2 代码访问工具（agentic 动态上下文）
评审过程中可按需调用工具查代码（白名单，防路径穿越 + token 截断）：
- `read_file`：读文件（行范围/截断）
- `grep`：正则搜索（找引用/定义）
- `ast_grep`：语法感知查询（函数定义/调用点）
- `list_dir`：目录浏览

**使用纪律**：跨文件影响面确认（如被改函数被谁调用）时**必须**用工具查，不能只凭 diff 猜。

## 三、评审执行

### 3.1 判断纪律（降低误报的核心）
1. **不假设**：不假设接口参数/状态管理方式/某个值"应该在别处"，只有看到证据才下结论
2. **结合契约**：以 AGENTS.md/spec 为据，contract 明确违反才报
3. **无法确认设计意图 → `needs_review=true`**（标"需人工确认"），不得当作确定性 bug
4. **约定违反必须报**：AGENTS.md 明确约定（如"error 必须处理""禁止硬编码密钥"）被 diff 触发就必须报，属于约定违反而非语言语义问题
5. **只审本 PR**：不评 diff 外的既有代码（除非被本 PR 破坏的调用方）

### 3.2 评审重点（review_focus，按需定制）
默认维度：bug / 安全 / 资源 / 约定 / 类型一致性（请求模型 vs 响应模型同名字段）。可通过配置覆盖。

### 3.3 生成代码排除
文件头含 `Generated by` / `@generated` / `DO NOT EDIT` 标记的自动跳过（如 orval 生成文件）。

### 3.4 大 diff 分批
- 单批 ≤ 20 文件，单文件 diff ≤ 800 行，超限截断/跳过
- 分批审查后合并结果

## 四、严重度（两轴锚定，策略插件）

**执行本步前加载 `review-severity-policy` skill**，按其当前版本执行：
- LLM 只输出 `trigger`/`impact` 两个事实判断
- 代码映射 1-5（确定性表）
- 硬性约束不可改；软性参数（如假设性最高 3）可按策略插件版本调整

## 五、输出格式（issues JSON）

```json
{
  "issues": [
    {
      "file": "src/foo.py",
      "line": 42,
      "locations": [{"file": "src/bar.py", "line": 10}],
      "trigger": "real | hypothetical | style",
      "impact": "fatal | functional | minor | none",
      "category": "bug | security | convention | design_intent | resource | type_consistency | other",
      "title": "简短标题",
      "suggestion": "具体可执行的修改建议（能给代码就给代码）",
      "evidence": "判断依据（引用代码/契约位置）",
      "needs_review": false
    }
  ],
  "summary": "整体评审摘要"
}
```

## 六、质量门（逐条验证 + 降级哨兵）⭐ v1.0 改造方向

> 说明：本版质量门是 2026-08-20 评审后的**目标设计**（借鉴 CodeRabbit Verification Agents
> 的"逐条验证"思路，替代旧版"整批打分+全量重写"）。ai-tools 代码当前仍为旧版，待对齐。

### 6.1 结构校验（零成本，直接执行，不是参考信号）
对每条 issue 确定性检查：
- 行号缺失 → 标记待删
- 行号不在 diff 新增行 → **疑似幻觉，待验证**
- `trigger/impact` 非法值 → 待修正
- **假设性证据 + 级别 ≥4**（触发"拦合并"的最贵误报）→ 待降级（按策略插件的软性参数，默认降到 3）

### 6.2 逐条验证（LLM 验证器，只对有嫌疑的跑）
对"待删/待降级/待修正"的 issue 跑轻量验证：
- 引用的代码行真实存在吗？（幻觉检测）
- 结论与代码证据一致吗？
- 保留 / 降级 / 删除，逐条决策

**成本控制**：对的不动，错的单独处理。验证只针对有嫌疑的少数，不是全量重来。

### 6.3 降级哨兵（异常路径，替代"整批重写"）
仅当**删除/降级比例异常高**（如 >30% 被处理）时，判定"本轮审查整体质量差"→ 才触发整批重审（带验证 reasons 作反馈）。正常情况不触发。

### 6.4 judge 模型路由
- judge/验证器**默认独立模型**（可配 `judge_provider`/`judge_model`），避免同模型自评偏差
- 默认不共用审查模型；成本增量小（验证输入远小于审查输入）

## 七、门禁

- `fail_on_severity`（默认 4）：存在 ≥4 的 issue → check failure，拦合并
- `needs_review` 标记的问题不计入门禁（避免误报阻塞）
- 评审质量降级（sentinel 触发且重审仍差）→ check neutral（不阻塞），发说明评论

## 九、与 pr-ai-review-loop 的协作

本 skill 是**评审环节**的实现；`pr-ai-review-loop` 是**迭代环节**（改代码→push→再评审）。
协作方式：
- loop 触发评审 → 加载本 skill 执行（或调用 ai-tools action）
- 本 skill 输出的 issues JSON 是 loop 判断"改不改、改什么"的输入
- loop 的 3 轮硬上限与人工介入报告，与本 skill 的质量门独立
